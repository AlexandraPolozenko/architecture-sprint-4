**Архитектурное решение по трейсингу**


**Системы, которые необходимо покрыть трейсингом**
Потенциальные проблемные места:
- Shop API: долгая обработка файла от пользователя и его отправка в storage, долгие походы в бд (статусы FILE_UPLOADED, SUBMITED)
- CRM API: долгая обработка файла в storage, походы в бд (статус MANUFACTURING_APPROVED)
- MES API: вычисление стоимости заказа, взаимодействие с бд (статус PRICE_CALCULATED )

Что добавлять в трейсинг:
- Идентификатор заказа
- Статус заказа
- Время поступление и обработки запроса
- Данные о сервисе
  

**Мотивация**
Трейсинг поможет:
- Быстрее находить проблемы после тестирования (понижение t2m)
- Быстрее находить проблемы во время инцидентов или критичных репортов пользователей (уменьшение времени недоступности)
- Увеличение капасити команды для продуктовых задач (разработчики быстрее находят причины проблем)
- Оптимизировать потребление ресурсов (доливать ресурсы не во всю систему, а только в необходимые части системы)
- Идентифицировать места, в которых происходят задержки => уменьшить время ответа апи => повысить CX пользователей


**Предлагаемое решение**
Для сбора данных предлагается использовать OpenTelemetry (который нужно будет добавить в Shop API, CRM API, MES API), а для их визуализации 
Jaeger (так же необходимо настроить).



**Компромиссы**
- Проприетарные системы
- Некритичная/редко используемая функциональность (мало запросов в апи => трейсинг избыточен)


**Безопасность**
Войти в систему могут только разработчики/devops/sre.
Пользовательские данные/данные аутентификации не передаются в трейсинг.
Критичные данные шифруются
