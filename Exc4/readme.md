**Архитектурное решение по логированию**


**Какие логи необходимо собрать**

Для всех логов в системе указываем время и cервис
- INFO Логируем изменение статуса заказа по всем микросервисам. Необходима информация об идентификаторе заказа и его статусе
  Для shop идентификатор клиента, для crm - продавца, для mes - оператора.
- TRACE Логируем получение данных из RabitMQ, походы в s3 storage, походы в бд, параметры вызовов апи (полученные и переданные данные, тайминги).
- ERROR Логируем недоступность любой из систем (в s3 закончилось место, mes не отвечает на запросы и пр)



**Мотивация**
- Быстрее находить проблемы после тестирования (понижение t2m)
- Быстрее находить проблемы во время инцидентов или критичных репортов пользователей (уменьшение времени недоступности)
- Увеличтиь капасити команды для продуктовых задач (разработчики быстрее находят причины проблем)
- Оптимизировать потребление ресурсов (доливать ресурсы не во всю систему, а только в необходимые части системы)
- Идентифицировать места, в которых происходят задержки => уменьшить время ответа апи => повысить CX пользователей

Логирование и трейсинг в первую очередь нужно настраивать для сервиса MES, т к на нем самые сложные вычислительные операции (потенциальное узкое 
место) и различные потребители апи.



**Предлагаемое решение**

Для работы с логами можно использовать стек ELK (Filebeat для агрегации данных, Logstash для изменения и сохранения 
данных, ElasticSearch для хранения и поиска данных, Kibana для визуализации и управления). Для внедрения логирования нужно настроить и подключить
все вышеперечисленное.

https://github.com/AlexandraPolozenko/architecture-sprint-4/blob/sprint-4/Exc4/jewerly_c4_model.drawio.png

Доступ к логам будут иметь разработчики, devops, sre и тестировщики. Персональные данные и данные авторизации логироваться не будут (либо данные 
будут маскироваться).

Оперативные логи хранятся до недели. Архивные логи - удвоенное время цикла производства (время производства заказа в p95).


**Превращение системы сбора логов в систему анализа логов**
- Настройка мониторинга по логам (дашборды с основными показателями, например количество error-логов, кол-во логов о каком-то статусе заказа и пр)
- Определение аномалий
- Настройка алертинга по аномалиям
